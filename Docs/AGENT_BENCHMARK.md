# BULL Agent Lab — MVP v0.24.0.0

Модуль проверяет результат автономной работы на конкретной задаче. Он не строит
универсальный рейтинг моделей и не смешивает результаты с обычными CHAT/CODE scores.
В MVP поддерживается Ollama с tool calling. Используется уже выбранное подключение:
локальное либо удалённое через существующий SSH-туннель.

В v0.24.0.0 Enter в настройках сохраняет текущие значения. Ошибка или отмена
редактирования не меняет прежнюю конфигурацию. Сбор ресурсов полностью фоновый:
первый sample может появиться после начала, последний — до завершения задачи.
Finish RAM/VRAM означает последний наблюдавшийся sample, а не точный замер при stop.
Недоступные/нечисловые датчики записываются как null. Прерванный JSON в истории
пропускается; исходный файл не удаляется.

## Запуск

1. Откройте **Тесты и результаты → Агентская задача** или
   `BULL-Agent-Lab-v0.24.0.0.cmd`.
2. Выберите **Настройки теста → Выбрать модель**. Модели берутся из каталога backend.
3. Для первого запуска можно оставить стандартные значения и нажать **S**. Контекст
   и лимиты редактируются отдельно; sampling и инструкции — в расширенных параметрах.
   0 отменяет весь черновик. Перед запуском нужно явно ввести **1**.
   Профильный `num_ctx`, уже загруженный context и запрошенный context — разные значения.
4. Откройте **Посмотреть задачу**, затем **Запустить агентскую задачу**.
5. После завершения прочитайте краткий итог; полная таблица и HTML открываются
   отдельными пунктами. Неудачные промежуточные проверки кода не считаются падениями
   приложения, отсутствующий датчик показывается как «нет данных».
   В **История и сравнение** выберите номера
   запусков через запятую. Доступны локальные JSON, CSV и HTML с context timeline.

История и отчёты работают без backend. Модуль создаёт чистую рабочую копию для каждой
попытки. Модель, которую Ollama не объявляет поддерживающей tools, не запускается.
MVP использует `think=false`; модели, требующие обязательного reasoning, могут быть
несовместимы. Скрытый reasoning не записывается даже при его выдаче backend.

## Что именно проверяется

`PYTHON_CART_FIX_001`, version 1 — исправление трёх функций расчёта корзины.
Нужно прочитать требования, найти ошибки вычисления количества и скидки, исправить
исходник и пройти 12 независимых проверок, включая пустую корзину, границы скидки и
округление. Это небольшой воспроизводимый coding workload, не Android/Gradle benchmark.

Инструменты: `list_files`, `read_file`, `write_file`, `run_tests`. Запись разрешена
только в `pricing.py`. Верификатор и тестовые данные расположены вне рабочей копии.
Заявление модели «готово» само по себе никогда не устанавливает SUCCESS.
После положительного run_tests финальное содержимое проверяется ещё раз.

Для безопасного первого этапа исходник **не выполняется Python через exec/import**.
Доверенный отдельный процесс интерпретирует ограниченное подмножество AST с лимитами
операций, размера значений и глубины вызовов. Импорты, атрибуты, shell, сеть и доступ
к ОС отсутствуют. Поддержанные конструкции перечислены в REQUIREMENTS.md задачи.
Такой тест измеряет работу в указанном harness; его результаты нельзя переносить
на произвольный coding agent или большой репозиторий без отдельной проверки.

Произвольные команды Gradle, pytest, npm, cargo и dotnet требуют следующего адаптера
изолированной среды с ограничениями файлов, сети, времени и ресурсов. Они не
запускаются автоматически в системе пользователя.

## Конфигурация и измерения

Сохраняются все семь sampling-параметров: temperature, top_p, top_k, min_p,
repeat_penalty, num_predict, seed. Backend получает их явно вместе с num_ctx.
Резерв `backend_context - agent_context` должен вмещать num_predict; малый запас
вызывает предупреждение. Установленный context проверяется через `/api/ps` после
ответа. Несовпадение даёт `configuration_mismatch`, а не успешный сопоставимый run.
Если backend не сообщает effective context, он остаётся неизвестным.

Настраиваются system prompt, agent instructions, project rules, tool-safety rules,
название/версия правил, число шагов, таймауты и стратегия контекста.
В результате остаются SHA-256 инструкций и footprint с пометкой **estimated**.
Жёсткие ограничения tools действуют независимо от текста инструкций модели.

Ollama возвращает фактический `prompt_eval_count` уже обработанного запроса.
Контекст до отправки, после tools, после compaction и footprint вычисляются приближённо:
UTF-8 bytes / 3 с поправкой вверх по наблюдаемому count. Это не точный tokenizer.
В таблице и графике фактический **пик входа запроса** отделён от оценённого пика контекста.
Проверка лимита перед запросом приблизительная; превышение фактического лимита
обнаруживается после ответа и останавливает run. Итоговый exact context после последнего
tool result недоступен без нового обращения к модели.

Compaction детерминированно удаляет старые полные циклы assistant/tools, сохраняет
постоянные инструкции, исходную задачу и последние циклы. Рабочие файлы остаются.
Модель получает сообщение о необходимости перечитать их. Это сокращение истории,
не LLM-summary. Сохраняются count, время, before/after и removed tokens (оценки).
Если постоянные инструкции и оставшийся хвост не помещаются, run останавливается.

Скорости считаются из суммарных токенов и суммарных длительностей, не средним
арифметическим отдельных tok/s. Длительности Ollama переводятся из наносекунд.
Токены/скорости относятся к завершённым запросам: при разрыве число уже потраченных
backend токенов может быть неизвестно. Это явно указано в llm_metric_scope; если
завершённый запрос не вернул обязательную метрику, её агрегат остаётся null.
`prompt_tps = prompt_eval_count / prompt_eval_duration` отражает throughput с влиянием
кеша; новые версии API могут отдельно отдавать `prompt_eval_cached_count` — он тоже
сохраняется. TTFT измеряется от отправки до первого непустого token/tool chunk;
отдельно хранится время до первого видимого content/tool chunk. Reasoning в лог не попадает.
Официальные контракты: [chat](https://docs.ollama.com/api/chat),
[running models](https://docs.ollama.com/api/ps),
[tool calling](https://docs.ollama.com/capabilities/tool-calling).

RAM/VRAM собираются периодически и на границах run. На Windows RAM доступна через
системный API, NVIDIA VRAM — через nvidia-smi. Для удалённого Windows backend используются
фиксированные read-only SSH-пробы. Отсутствие доступа или другой GPU означает null,
не ноль. Области `client`, `backend`, `client_and_backend` не складываются и не подменяют
друг друга. Снимок CPU/OS/GPU backend — best effort. Пик — максимум выборки,
короткие всплески между измерениями могут быть пропущены. Инструментирование и
независимая проверка входят в total duration; useful completion отмечается отдельно.

Метрики автономности: success с независимой проверкой; autonomous_success только
при отсутствии вмешательств; время до подтверждённого результата; доля неуспешных
tools; interventions/task; compactions/10000 processed prompt tokens. Деление на
ноль или отсутствующие измерения даёт null.

## Сбои и вмешательства

Каждый request/tool-start и завершённый шаг сохраняет `result.json` атомарно с fsync.
Различаются connection_reset, connection_refused, timeout, context_overflow,
HTTP/model errors, malformed_tool_call, build_test_failure, agent_loop и другие причины.
Аргументы одинаковых tool calls сравниваются в памяти; повторения отмечаются отдельно.
Четыре одинаковых последовательных вызова по умолчанию останавливают run как loop.

Ctrl+C во время model request открывает выбор: повторить запрос, скорректировать
задачу, ответить на вопрос или завершить попытку. Ручное действие учитывается.
Изменение рабочего файла извне обнаруживается на границах шагов; краткие изменения
между двумя проверками могут остаться незамеченными. Внешние tools, не проходящие
через этот harness, автоматически не наблюдаются.

После аварийного завершения процесса/перезагрузки последний result может иметь
status=running: это незавершённая запись, не SUCCESS. История позволяет **повторить
первый run с начала**. Создаётся новый run_id с parent_run_id и чистой fixture;
предыдущая попытка не перезаписывается. Для прерванного родителя фиксируется manual_retry,
поэтому такой новый успех не выдаётся за полностью автономный. Полноценное восстановление
агентской истории с середины задачи в MVP не реализовано.

## Файлы и приватность

- `Runtime/agent_configuration.json` — текущая приватная конфигурация.
- `Benchmarks/Agents/<run_id>/configuration.private.json` — точная конфигурация для повтора.
- `Benchmarks/Agents/<run_id>/workspace/` — только рабочие файлы задачи.
- `Benchmarks/Agents/<run_id>/result.json` — метрики, контекстные точки и события.
- `Benchmarks/Agents/<run_id>/report.html` — автономный отчёт без JavaScript/CDN.
- `Benchmarks/Agents/comparison.html` / `.csv` — последний явно созданный экспорт.

Схемы config/run имеют собственное имя и schema_version=1. Переносимый result не
содержит тексты prompts/rules, reasoning, аргументы/ответы tools, raw exceptions,
пути ключей или environment. Для tools сохраняются имя, размеры, время, успешность,
ошибка-категория, repeat/retry counters. События диагностические, не внутренние мысли.
CSV обезвреживает формулы; HTML экранирует текст и не загружает внешние ресурсы.

Приватная конфигурация намеренно хранит введённые инструкции для воспроизводимости.
Не вставляйте в них credentials. Рабочие исходники и выбранные имена моделей тоже
могут быть приватны. Перед ручной передачей файла проверяйте его содержимое.
Все эти пути исключены из публичного ZIP и Git. Export — отдельное действие пользователя.

## Следующий этап: Agent Tuning

MVP позволяет вручную менять параметры, повторять тест и сравнивать несколько runs.
Автоматический перебор context/sampling/models, сбалансированный порядок, repeats,
SD/интервалы, regression detection и Windows paging/CPU/GPU time series — следующий этап.
Для него понадобятся отдельные задачи с независимыми версиями, validation set против
переобучения на единственной fixture и адаптер реальных изолированных сборок.
Даже после его добавления один универсальный score или автоматический «лучший вариант»
не планируется: пользователь видит результат, автономность, время и ресурсы отдельно.
