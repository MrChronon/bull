# BULL v0.28.0.5 — руководство пользователя

[Краткое актуальное руководство](ru/USER_GUIDE.md) · [English user guide](en/USER_GUIDE.md)

**Версия клиента:** v0.28.0.5

**Версия документации:** v0.28.0.5

BULL — Benchmark Lab — переносимое приложение для Windows 11, которое объединяет рабочий чат с локальными LLM и лабораторию воспроизводимого сравнения моделей. Поддерживаются Ollama и совместимый с OpenAI API сервер llama.cpp. Модели могут работать на том же компьютере или на отдельном узле, доступном через защищённое SSH-соединение.

Версия документа: 5 октября 2026 года. История изменений вынесена в `Docs/CHANGELOG_v0.28.0.5.md`.

### Что изменилось в v0.28.0.5

v0.28.0.5 продолжает **Simple Experience** и добавляет **Clear Benchmark Flow**. Главное меню
по-прежнему отвечает четырём обычным задачам: сравнить модели, открыть чат, выбрать подключение и перейти к
дополнительным функциям. Agent Lab, GPU Lab, ручная серверная настройка и точные
`/bench`-команды сохранены, но перенесены в дополнительные или экспериментальные
разделы. Ничего из прежнего функционала не удалено.

После прогона BULL показывает краткую сводку прямо в терминале. Для каждого
сопоставимого запуска отмечаются модели для профилей **Качество**, **Скорость**,
**Баланс** и **Мало памяти**. Можно ввести собственные веса качества, скорости,
выполнения контракта и VRAM. Эти профили — прозрачная относительная подсказка
внутри одного прогона, а не новый quality score. Скоростные рекомендации проходят
явный quality/task gate. Терминал и автономный HTML показывают двумерную карту
«Native quality ↔ скорость», а меню отдельно предлагает share-safe summary JSON,
HTML и помечает raw JSON как приватный.

Папка `UserTests` теперь содержит три самодостаточных синтетических шаблона.
Простой UTF-8 `.txt` позволяет прогнать один prompt
по выбранным моделям без выдуманного автоматического балла. Строгий `.yaml`
задаёт версионированный контракт и только детерминированные критерии. Формат не
исполняет код, YAML tags, aliases или регулярные выражения. Поддерживаемые типы,
веса, critical cap, числовые допуски и правила написания prompt подробно описаны
в `Docs/USER_TESTS.md`; готовые шаблоны находятся в самой папке.

Полная пиксельная голова быка и расшифровка названия показываются на каждом
навигационном экране. Язык выбирается один раз при первом запуске и позднее
меняется вместе с темой через **Дополнительно → Язык и внешний вид**. Доступны
красная BULL по умолчанию, зелёная Matrix BULL и высококонтрастная темы. Во время
стартовой проверки отдельное окно показывает текущую проверку и реальный
прогресс: число завершённых проверок из общего количества.
Встроенные benchmark
prompts, scorers, recovery и inference runtime этого релиза не переписывались;
изменён только изолированный scorer пользовательских YAML-контрактов.
При выборе моделей можно использовать номера с пробелами после запятых, например
`2, 4, 7`. После выбора preset следующий экран параметров открывается отдельно,
поэтому старое меню не остаётся под новым. Во время прогона, если это доступно на
активном узле, строка live telemetry показывает CPU и RAM рядом с GPU и VRAM. После
каждого сохранённого run BULL печатает короткий checkpoint с результатом, скоростью
и измеренными ресурсами.

Подробности: `Docs/RELEASE_NOTES_0.28.0.5.md`.

Важно: старые исполняемые CODE-наборы не имеют полноценной OS-песочницы. Для
недоверенных ответов используйте отдельную disposable VM без секретов и сети.
Это не относится к ограниченному интерпретатору новой Agent-задачи. Python tool
чата после подтверждения RUN также работает с правами пользователя.

## 1. Что входит в приложение

- **LLM Client** — обычные диалоги, режимы FAST, THINK и ULTIMATE, сохранение сессий и импорт проверенного benchmark-профиля.
- **Benchmark Lab** — готовые тесты, собственные промпты, сравнение нескольких моделей, checkpoint/resume, сводная аналитика и автономный HTML-отчёт.
- **Agent Benchmark (MVP)** — многошаговая coding-задача, независимая проверка успеха, измерения автономности и ресурсов, сравнение конфигураций. Подробности: `Docs/AGENT_BENCHMARK.md`.
- **BULL Core** — общие typed contracts, backend adapters, profiles, schemas,
  telemetry, atomic artifacts и report boundary без зависимости от UI.
- **BULL Registry** — versioned data-only benchmark packs, validation, gold
  snapshots и воспроизводимые hashes без выполнения кода из pack.
- **BULL Evidence** — immutable provenance, раздельные пространства метрик,
  private/share-safe artifacts и единые данные для terminal/HTML reports.
- **BULL RU Dialogue** — public candidate pack с 10 параметризованными кейсами,
  раздельными semantic/structural scores и auditable critical failures.
- **Server role** — настройка inference-узла без выдачи клиенту доступа к чужим ключам или конфигурациям.

Языковые модели в архив не входят. Установите их отдельно и соблюдайте их лицензии.

## 2. Быстрый старт

1. Распакуйте релиз в новую папку.
2. По возможности сравните SHA-256 архива с опубликованным файлом `.sha256.txt`.
3. Запустите `Install-BULL-v0.28.0.5.cmd`. Установщик создаст ярлыки BULL на
   рабочем столе и в меню «Пуск» с красной фирменной иконкой.
4. Выберите роль:
   - `Client` — чат и Benchmark Lab для уже доступного backend;
   - `Server` — подготовка компьютера с моделями;
   - `AllInOne` — клиент и backend на одной машине.
5. Для основного приложения используйте `BULL-v0.28.0.5.cmd`.
6. Для прямого входа в лабораторию используйте `BULL-Benchmark-Lab-v0.28.0.5.cmd`.

При первом запуске выберите **English** или **Русский**. Этот вопрос больше не
появляется после сохранения выбора. Язык и цветовая тема меняются в приложении:
**Дополнительно → Язык и внешний вид**.

При первом запуске выполняется offline regression. Во время неё BULL открывает отдельное небольшое окно с версией, иллюстрацией, названием текущей проверки и реальным счётчиком завершённых проверок из общего числа. После проверки окно закрывается, а затем открывается основной экран. Это окно не меняет палитру терминала. Если графическая подсистема Windows недоступна, проверка всё равно выполняется, а BULL продолжает запуск в терминале. Если проверка не прошла, inference и benchmark блокируются: сначала устраните причину или повторите `Run-Tests.ps1`.
Для запуска Client и полного startup regression достаточно стандартной библиотеки
Python: Pillow и другие сторонние Python-пакеты не требуются. Pillow нужен только
разработчику, который заново генерирует брендовые raster assets.

Installer и все launchers совместимы с Windows PowerShell
5.1. Архив обязательно содержит программный модуль `Shared/bull_llm/runtime`;
корневой `Runtime` по-прежнему считается приватными пользовательскими данными и
в публичный ZIP не входит. В bundle больше нет дублирующих legacy launchers или
старого Python namespace.

Работающее локальное API при старте не обязательно. Если Ollama или удалённая лаборатория временно недоступны, клиент всё равно открывает главное меню со статусом `offline`. Настройки, помощь и сохранённые HTML-отчёты доступны без backend. Экран состояния в этом режиме показывает выбранную цель и последние сохранённые значения, явно помечает отсутствие живой диагностики и не запускает telemetry-запрос. Подключение проверяется один раз непосредственно перед новым чатом или benchmark; приложение не меняет выбранный backend автоматически.

## 3. Главное меню

Основные действия сформулированы по задаче пользователя:

1. **Сравнить модели** — стандартный сопоставимый прогон, пользовательская задача,
   восстановление или просмотр сохранённого результата.
2. **Чат с моделью** — начать диалог или открыть сохранённую сессию.
3. **Подключение** — этот компьютер, сохранённый сервер или SSH-алиас.
4. **Дополнительно** — результаты, внешний вид, диагностика, справка, команды и
   экспериментальные возможности.

**0 — Выйти:** закрыть программу.

Опытный пользователь по-прежнему может ввести команду с `/` вместо номера на
главной, но этот путь не занимает отдельный пункт меню. Пути и аргументы не
переводятся в нижний регистр. После выполнения команды результат остаётся на экране
до Enter, затем открывается главная; `/load` открывает диалог. `/menu` и `/home`
ведут в одно главное меню. Обычный текст для модели вводится только в чате.

Цвет не является единственным индикатором состояния: важные статусы всегда имеют текстовую подпись.

## 4. Локальная работа

### Ollama

Установите Ollama, загрузите модель и убедитесь, что локальный API доступен только на loopback. Свежая установка BULL использует локальный режим и не пытается открыть SSH-соединение.

Примеры внешних команд:

```powershell
ollama list
ollama run MODEL_NAME
```

В приложении выберите **Подключение → Использовать этот компьютер**.

### llama.cpp

Запустите совместимый HTTP server на `127.0.0.1`. Если адрес не loopback, приложение по умолчанию требует HTTPS и Bearer key. HTTP redirects блокируются, чтобы заголовок авторизации не ушёл на другой узел.

### AllInOne

Роль AllInOne подходит для ноутбука или рабочей станции, где одновременно находятся клиент и модели. Для такого сценария не нужен connection bundle или SSH-ключ.

## 5. Удалённая лаборатория

Рекомендуемая схема — inference API слушает только loopback удалённой машины, а клиент подключается через SSH tunnel. Не публикуйте Ollama `11434` или llama.cpp `8080` напрямую в Интернет.

BULL разделяет:

- публичное описание подключения: тип, адрес, порт и fingerprint;
- приватный SSH-ключ, который остаётся только у владельца клиента;
- runtime connection store, который не входит в релиз.

Свежий публичный архив не знает адреса, имени пользователя или ключа какого-либо частного сервера.

### Быстро: уже настроенный SSH-алиас

Если `ssh bull-home` уже работает по ключу:

1. Откройте **Подключение → Добавить по SSH-алиасу**.
2. Введите имя из строки `Host` в `%USERPROFILE%\.ssh\config`, например `bull-home`.
3. Проверьте найденные адрес, пользователя, порт и `IdentityFile`.
4. Если host key совпадает с вашим OpenSSH `known_hosts`, BULL использует это
   существующее доверие. Иначе мастер потребует независимо проверенный fingerprint.
5. Выберите постоянное или временное сохранение и сразу проверьте подключение.

Быстрый путь поддерживает прямой SSH и намеренно не импортирует `ProxyCommand` или
`ProxyJump`. Приватный ключ должен существовать как `IdentityFile`; его содержимое
не читается и не копируется. Пошаговое создание ключа, alias и `ssh-agent` описано
в `Docs/SSH_QUICKSTART.md` и доступно прямо в меню **Как создать SSH-ключ и алиас**.

### Вручную: новый адрес

Если алиаса ещё нет или нужны нестандартные параметры:

1. Откройте **Подключение → Добавить сервер вручную**.
2. Введите IP/DNS (без `http://`), имя SSH-пользователя, внешний SSH-порт и путь к приватному ключу без `.pub`.
3. Оставьте стандартный порт Ollama `11434` или откройте настройку другого порта.
4. Мастер получит публичный Ed25519 ключ сервера. Вставьте fingerprint `SHA256:…`, независимо полученный **на сервере** или у администратора; не копируйте вслепую показанное мастером значение. Команды проверки показаны на экране. При несовпадении сохранение запрещено.
5. Проверьте итог. Выберите **Сохранить для следующих версий и подключиться** либо **Подключиться только из этого билда**. Enter и 0 отменяют сохранение.

Для ключа с паролем заранее добавьте его в `ssh-agent`: приложение не сохраняет
пароли и не запрашивает их в SSH batch mode. Ключ должен быть заранее разрешён на
сервере. Мастер не устанавливает сервер, не меняет firewall/роутер и не загружает модели.
Нестандартный host-key алгоритм: импортируйте доверенный Connection JSON через
**Подключение → Импорт и перенос → Импорт Connection JSON**.

На Windows личная адресная книга находится в `%LOCALAPPDATA%\BULL\connections`.
Это приватные метаданные: адрес, пользователь, публичный ключ сервера и **путь** к
вашему приватному ключу. Содержимое ключа не копируется. Адресная книга не зашифрована,
защищается правами профиля Windows и никогда не входит в ZIP. Храните ключ вне папки
удаляемого билда. В новом билде выберите **Подключение → Выбрать сохранённый сервер**
и подтвердите подключение. Автоматического выбора сервера по адресной книге нет.

Первый переход со старой версии: **Подключение → Импорт и перенос → Перенести из старой
версии**, затем укажите папку билда. Для старых ручных SSH-профилей потребуется
повторно подтвердить fingerprint. Полный `backend_settings.json` поверх новой версии
копировать не нужно. Удаление записи из адресной книги не удаляет ключ и не отзывает
доступ на сервере; текущий Runtime остаётся неизменным.

После импорта или выбора сервера не нужно перезапускать приложение и вручную выходить из нескольких меню: клиент сразу выходит к проверке выбранного подключения. Если проверка не прошла, конфигурация сохраняется, выводится конкретная ошибка, а пользователь возвращается в главное меню без переключения на локальную Ollama.

Поддерживаются локальная сеть, VPN и доступ через Интернет при условии безопасной настройки SSH. Подробности: `Docs/REMOTE_ACCESS.md` и `Docs/BACKEND_SETUP.md`.

### Интернет через белый IP

В меню **Подключение → Помощь и диагностика → Инструкция по доступу через Интернет** показана последовательность Server → router/NAT → Client. Приложение не включает UPnP и не меняет роутер автоматически.

Для direct-доступа наружу публикуется только SSH-порт. Рекомендуемая схема:

```text
Client -> PUBLIC_IP:EXTERNAL_SSH_PORT -> router -> SERVER_LAN_IP:22
       -> SSH tunnel -> 127.0.0.1:11434
```

Ollama остаётся доступна только через SSH-туннель. Не перенаправляйте на роутере `11434`, `11435`, `8080` или RDP. Перед отъездом закрепите LAN-IP сервера, проверьте automatic startup `sshd` и выполните внешний тест через мобильный интернет. Проверка из домашнего Wi-Fi может не работать из-за отсутствия NAT loopback даже при корректном внешнем доступе.

## 6. Рабочий LLM Client

### Режимы

- **FAST** — обычный ответ с ограниченным бюджетом.
- **THINK** — reasoning, только если backend и профиль модели действительно его поддерживают.
- **ULTIMATE** — продолжительный bounded workflow с переносом рабочего checkpoint; не означает неограниченное выполнение.

Фактический режим сохраняется отдельно от запрошенного. Если модель не поддерживает THINK, fallback фиксируется в telemetry и не маскируется.

### Диалоги и файлы

Сессии сохраняются локально. Экспорт может содержать пользовательский текст, ответы, локальные пути и метаданные модели. Перед публикацией или отправкой диагностик просмотрите файл вручную.

### Проверенные профили

Benchmark Lab может сохранить версионированный JSON с протестированной конфигурацией. Client импортирует выбранный профиль явно; benchmark не меняет рабочие настройки незаметно.

Экспорт объединяет записи с одинаковыми настройками, пригодными для Client, даже
если benchmark-specific fingerprints отличаются из-за prompt budget или теста.
Seeds остаются частью доказательной базы, но не импортируются в рабочий чат:
иначе первый seed прогона незаметно сделал бы обычные ответы детерминированными.
Артефакт хранит полный список исходных effective-profile fingerprints. Метка
`tested_not_ranked` означает «проверен и готов к явному импорту», а не автоматическую
рекомендацию одной модели или конфигурации над другой.

## 7. Benchmark Lab

### Основные сценарии

1. **Сравнить модели** — рекомендуемый CHAT-набор, три seeds и сбалансированный порядок.
2. **Тест по своему промпту** — вставить задачу, выбрать модели и простой preset.
3. **Восстановить и продолжить** — продолжить checkpoint после сбоя.
4. **Открыть результаты** — открыть автономный HTML-отчёт.
5. **Агентская задача** — независимая проверка исправления тестового проекта.
6. **Расширенные тесты** — single test, category, full matrix, rescore, sweep и точная CLI-команда.
7. **Экспериментальная GPU Lab** — отдельная Ollama на выбранных NVIDIA GPU;
   производительность, датчики, сравнение одиночных карт и комбинации. Windows локально или по SSH.

### Свой промпт

`prompts.json` является индексом, а не единственным перезаписываемым текстом. Новый промпт получает отдельную запись. Редактирование сохранённого промпта создаёт новую неизменяемую версию в `Benchmarks/Prompts/...`; старая версия остаётся в истории. Checkpoint фиксирует точную версию и SHA-256, использованную в прогоне.

Стандартный preset:

- 3 seeds;
- native pipeline;
- fair profile;
- job-level counterbalanced-порядок: модели и тесты вращаются между волнами, а
  seeds распределяются по разным ранним, средним и поздним позициям.

Быстрый preset с одним seed проверяет работоспособность, но не даёт устойчивой оценки ранжирования.

### Готовый CHAT-набор

CHAT core включает задачи на:

- русский язык и деловой стиль;
- состояние и исправления в диалоге;
- groundedness и сопротивление инструкциям, встроенным в данные;
- точное выполнение ограничений;
- причинную осторожность;
- логику.

Качество кода и специализированная аналитика оцениваются отдельными категориями и не смешиваются с CHAT-рейтингом.

### BULL RU Dialogue (candidate)

Новый pack отображается в каталоге как отдельные тесты с префиксом
`ru_dialogue_`. Его можно запустить через **Расширенные тесты → Один тест**,
**Одну категорию** или командой `/bench list`, а сведения о pack посмотреть через:

```text
/bench pack inspect bull_ru_dialogue
```

В pack входят 10 вариантов из шести семейств: confirmed state, evidence limits,
causal caution, instruction retention, business Russian и embedded-instruction
resistance. `semantic_score` оценивает согласованность фактов и запретных
утверждений; `structural_score` — terminal JSON, точную схему, секции и формат.
Один показатель не заменяет другой. Critical failure всегда требует просмотра
ответа человеком; автоматический cap — сигнал для аудита, а не диагноз модели.

Файлы `development_set.json`, `scorer_gold.json` и `manual_audit.json` открыты для
review. `Tools/build_ru_dialogue_pack.py` детерминированно создаёт runnable pack.
Не редактируйте сгенерированные `cases.json`, hashes или lock вручную.

### Источник параметров генерации

Перед сравнением нескольких моделей Benchmark Lab предлагает однозначный выбор:

- **Единые настройки бенчмарка** (`benchmark_override`) — прежнее поведение и режим по умолчанию. Один sampling preset передаётся всем моделям через API. Он подходит для сравнения разных моделей в одинаковых условиях.
- **Настройки Ollama-профиля** (`model_profile`) — перед запуском приложение читает актуальный Modelfile через `/api/show`. `temperature`, `top_p`, `top_k`, `min_p`, penalties и mirostat-параметры не добавляются в `options`; Ollama наследует их из профиля модели.
- **Отдельные настройки для каждой модели** (`per_model`) — пользователь заполняет редактируемую таблицу. Эти значения явно передаются через API и сохраняются как `per_model_override`.

В `model_profile` глобальный sampling preset отключён. Если параметр отсутствует в Modelfile, программа не подставляет предполагаемое значение и записывает `backend_default_unresolved`. Смешивание наследования Modelfile с runtime sampling override блокируется, пока пользователь явно не подтвердит mixed-режим.

Перед inference выводится матрица `Profile / Request / Effective / Source`. В JSON и CSV отдельно сохраняются `profile_parameters`, точный `sent_runtime_options`, источник каждого параметра, digest модели, версия Ollama и время чтения профиля. Поэтому значение из локального `model_profiles.json` больше не маскируется под фактический `profile_ctx`: при доступном `/api/show` поле берётся из `num_ctx` Ollama-профиля.

Для sampling-эксперимента задаётся `experimental_parameters`. `strict_fair_compare` разрешает различия только в этом списке; контекст, threads, thinking, `num_predict`, recovery и prompt должны оставаться сопоставимыми. Если заявленные экспериментальные параметры одинаковы у всех моделей, inference не начинается и выводится `SAMPLING_EXPERIMENT_HAS_NO_VARIATION`. Если режим профиля неожиданно отправляет sampling options, запуск блокируется кодом `MODEL_PROFILE_SAMPLING_OVERRIDDEN`.

Пример экспертной команды:

```text
/bench compare TEST all 3 native manual profile=ollama_profile_compare seeds=42,43,44 sampling_source=model_profile experimental_parameters=temperature,top_p,top_k,min_p
```

Старый результат, созданный с неверными runtime options, нельзя исправить offline rescore: ответы уже сгенерированы в других условиях. Нужен новый inference. Для сравнения code-настроек выбирайте CODE-категорию, а не CHAT-рейтинг.

### Native и Final system

- **Native model quality** — первый ответ модели до recovery.
- **Final system quality** — результат после разрешённого recovery/finalizer.

Эти показатели нельзя объединять в один рейтинг: первый характеризует наблюдаемое поведение модели, второй — весь клиентский pipeline.

### GEN, TASK и схема

- **GEN / Generation** — backend закончил выдачу без технического обрыва или исчерпания лимита.
- **Structural completion** — присутствуют требуемые блоки или терминальный результат.
- **Schema exact** — структура JSON точно соответствует контракту.
- **TASK / Task contract** — генерация завершена и обязательные структура/схема соблюдены.
- **REC.USED** — доля runs, где клиент использовал recovery; это не score модели.

Ответ может иметь `GEN=100%` и одновременно `TASK<100%`. Это означает законченную выдачу с нарушением формата, а не сетевой обрыв.

### Сводка в окне программы

После теста терминал показывает:

- Native и Final system score;
- GEN, TASK и REC.USED;
- полный worst test и число критических случаев;
- SD, min/max и worst seed;
- warm tok/s, GPU/VRAM, а также средние и пиковые CPU/RAM для каждого run, когда датчики доступны;
- наблюдаемого лидера качества, скорости и стабильности;
- лидеров категорий;
- предупреждение о пересечении 95% интервалов неопределённости.

Это описательная аналитика конкретного прогона, а не доказательство общего превосходства модели.

Во время прогона одна строка live-статуса показывает приблизительную скорость,
GPU/VRAM, CPU и RAM активного inference-host. После каждого сохранённого run BULL
добавляет короткий промежуточный итог: native/final score при наличии scorer,
TASK, скорость и измеренные ресурсы. Значения отсутствуют, если сервер не может
безопасно предоставить соответствующий агрегированный датчик; отсутствие значения
не интерпретируется как ноль.

### HTML-отчёт

Рядом с raw JSON создаётся `*_report.html`. Он автономный, работает offline, не
использует JavaScript/CDN и не встраивает prompts или raw-ответы. В нём есть шкалы
качества, warm speed, таблицы, category heatmap, Generation/Task contract,
confidence intervals, latency distributions, context curves и предупреждения о
недостаточной выборке. Если для curve или CI точек недостаточно, отчёт говорит об
этом прямо и не рисует ложную тенденцию.

### Файлы результата

Обычный прогон создаёт:

- raw JSON и плоский CSV;
- summary JSON и CSV;
- `*_evidence_private.json` — приватный `bull-benchmark-record` с исходными
  records и полным provenance;
- `*_evidence_share_safe.json` — allow-listed `bull-benchmark-summary`, прошедший
  автоматический privacy audit;
- checkpoint JSON;
- tested profiles JSON;
- HTML report.

Raw JSON и evidence private содержат ответы модели и могут содержать
пользовательский промпт в snapshot. Не публикуйте их. Share-safe JSON и HTML
предназначены для передачи метрик, но имена моделей всё равно могут раскрывать
локальную номенклатуру: просмотрите их перед публикацией.

## 8. Сбои и resume

Этот раздел описывает обычный Benchmark Lab. У Agent Benchmark собственная история:
ручной retry запроса учитывается как вмешательство, а после перезагрузки предлагается
новая чистая попытка со ссылкой на прерванную. Подробности и ограничения MVP приведены
в `Docs/AGENT_BENCHMARK.md`.

Checkpoint записывается атомарно. После потери сети, перезапуска backend или компьютера:

1. Запустите приложение снова.
2. Откройте Benchmark Lab.
3. Выберите **Восстановить и продолжить** или выполните `/bench resume`.
4. Клиент сбросит stale transport, ограниченно повторит соединение и проверит каталог моделей.
5. Завершённые records останутся сохранены; только незавершённый active run начнётся с начала.

Если backend ещё недоступен, checkpoint остаётся на паузе. Повторный resume не удаляет готовые результаты. Если inference уже закончен и осталась только финализация файлов, backend не требуется.

Не продолжайте один checkpoint в двух экземплярах одновременно. Новая версия
клиента считается изменением окружения: сначала завершите старый прогон в старом
bundle. Не используйте resume force просто для обхода предупреждения о версии.

## 9. Offline rescore

Rescore пересчитывает scorers по уже сохранённым ответам без запуска модели:

```text
/bench rescore PATH_TO_RAW_JSON
```

Исходный файл не меняется и проверяется по SHA-256. Создаются новые файлы с суффиксом версии, score diff и обновлённый HTML. В переносимые метаданные записывается только имя исходного файла, а не абсолютный домашний путь.

Rescore не делает старые prompts эквивалентными новым: для известных исторических версий применяется совместимый audit, а неизвестные версии помечаются как требующие ручной проверки.

## 10. Как читать статистику

- **Mean** — среднее по сопоставимым runs.
- **SD** — разброс; для одного seed недоступен.
- **Min / Max** — наблюдаемые границы.
- **Worst seed** — seed с минимальным score.
- **Rank stability** — насколько сохраняется порядок моделей между seeds.
- **Warm average** — скорость runs, признанных warm по фактическому load duration.
- **Pareto** — осторожная диагностика качества и времени с учётом 95% интервалов; при недостатке данных вывод не строится.

В новых запусках порядок моделей, тестов и seeds балансируется волнами. Модель
загружается один раз на волну, а не перед каждым тестом; cold/warm по-прежнему
определяется по фактическому `load_duration`. Старый checkpoint при resume сохраняет
исходный порядок, чтобы не менять уже начатый эксперимент. Полностью устранить
влияние температуры, фоновой нагрузки, thermal throttling и кеша невозможно. Для
решений используйте несколько запусков на неизменной системе.

## 11. Безопасность и приватность

Публичный release не должен содержать:

- `Chats`, `Runtime`, `Benchmarks`, `Exports`;
- `client_debug.log`, `ui_settings.json`, `.env`, `known_hosts`;
- private keys, tokens, passwords;
- реальные endpoints, usernames, e-mail и домашние пути;
- локальные model paths или частные benchmark results.

Перед публикацией запускайте:

```powershell
.\Test-Public-Release.ps1
.\Run-Tests.ps1
```

Для полной сборки используйте `Build-Release.ps1`: он дополнительно проверяет cp1251, PowerShell syntax, manifest, staged tree и ZIP.

Никогда не прикладывайте лог или raw benchmark к GitHub issue без просмотра. Используйте placeholders и удаляйте адреса, имена, пути, prompts и ответы.

## 12. Диагностика

### Backend отклоняет соединение

Проверьте, что сервис запущен, SSH tunnel восстановлен и выбран правильный connection bundle. После reboot удалённого узла дождитесь запуска inference server и повторите resume.

### WinError 10054 / 10061

- `10054` — существующее соединение было разорвано;
- `10061` — на целевом порту сейчас никто не принимает подключение.

Benchmark ставится на паузу; готовые runs остаются в checkpoint.

### Regression failed

Запустите `Run-Tests.ps1` из корня bundle. Не отключайте fail-closed поведение: оно защищает от выдачи недостоверных benchmark-результатов.

В исправленной сборке v0.24.0.0 пользовательский `backend_settings.json` не сравнивается с заводским шаблоном во время обычного запуска. Выбор локального или удалённого backend больше не может сам по себе сломать regression-проверку. Чистота публичного шаблона по-прежнему проверяется отдельно при сборке релиза. На экране показывается короткая причина из конца вывода, а полный диагностический текст записывается в локальный `client_debug.log`.

### Кракозябры в консоли

Запускайте `.cmd`/`.ps1` из Windows Terminal или PowerShell. Release gate отдельно проверяет запуск при cp1251, но шрифт терминала должен поддерживать Unicode.

### HTML не открывается

Откройте файл `*_report.html` вручную в современном браузере. Сетевое соединение для отчёта не требуется.

## 13. Команды для опытных пользователей

В Benchmark Advanced разрешены только `/bench ...` команды; произвольный текст не отправляется активной модели.

Полный синтаксис выводится через:

```text
/bench help
```

Основные команды:

```text
/bench list
/bench pack list
/bench pack validate [PACK_ID[@VERSION]]
/bench pack inspect PACK_ID[@VERSION]
/bench run TEST MODEL
/bench compare TEST MODELS
/bench category CATEGORY MODELS
/bench all MODELS
/bench resume
/bench rescore PATH
/bench report [PATH]
```

Перед запуском приложение показывает точный план: тесты, модели, seeds, pipeline, reasoning и порядок.

## 14. Ограничения релиза

- Приложение ориентировано на Windows 11.
- Модели и inference runtimes не входят в ZIP.
- Автоматический scorer не заменяет экспертную оценку открытых ответов.
- Один benchmark run не доказывает общее качество модели.
- Безопасность удалённого сервера зависит от корректной настройки ОС, SSH/VPN и firewall.
- Открытая публикация репозитория сама по себе не даёт права копировать или распространять код: владелец должен отдельно выбрать и добавить `LICENSE`.
