# BULL v0.29.0.1 — как писать запросы и выбирать режим

**Версия документации:** v0.29.0.1

**Актуализировано:** 11 октября 2026; локальный кандидат релиза.

**Назначение:** практическое руководство по рабочим prompt в BULL.

v17.3.2 — замороженная историческая baseline, не версия этого руководства.
Меню, установка и ограничения приёмки описаны в [руководстве](USER_GUIDE.md)
и [готовности релиза](RELEASE_READINESS.md).

## 1. Самое короткое правило

Используй:

- **FAST**: короткие и обычные задачи;
- **THINK**: сложная аналитика, статистика, программирование, многошаговый SQL;
- **ULTIMATE**: задача действительно сложная и THINK не успевает закончить решение в одном контексте.

Не выбирай ULTIMATE автоматически. Он может потратить во много раз больше времени и токенов.

THINK требует поддержки модели/backend. Заведомо неподдерживаемая модель в чате
использует FAST. Только явный HTTP 400 «does not support thinking» допускает один
повтор без THINK при выключенных tools; другие ошибки и benchmark-политика не
подменяются. Не трактуй название режима как подтверждение поддержки модели.

В клиенте:

```text
/think off
/think on
/ultimate on
/ultimate off
/help modes
```

## 2. Хороший prompt: пять частей

Для рабочих задач лучше всего явно задать:

```text
1. Цель
2. Данные / контекст
3. Правила и ограничения
4. Формат результата
5. Что перепроверить
```

Шаблон:

```text
Задача:
<что нужно получить>

Данные:
<таблица, код, описание, условия>

Правила:
<что считать, что исключать, определения>

Верни:
<формат результата>

Проверь:
<арифметика, крайние случаи, статистические допущения и т.д.>
```

Такой prompt обычно лучше фразы вроде:

```text
проанализируй это максимально умно
```

Потому что качество сильно зависит не только от reasoning, но и от однозначности самой задачи.

## 3. Как писать аналитический запрос

Для Data / BI / Product Analytics особенно полезно определить:

- grain: одна строка что означает;
- период анализа;
- границы интервала;
- правило дедупликации;
- denominator;
- что считать событием;
- как учитывать нулевые значения;
- как учитывать missing values;
- единицы измерения;
- статистический тест и alpha, если они заданы;
- нужен ли продуктовый вывод или только расчёт.

Пример:

```text
Задача:
Рассчитай D7 retention по дате регистрации.

Данные:
events(user_id, event_time, event_name).

Правила:
- регистрация = самое раннее событие registration пользователя;
- D7 = активность на 7-й календарный день после даты регистрации;
- это не >= 7 дней и не ровно 168 часов;
- один пользователь учитывается максимум один раз в числителе;
- пользователи без активности остаются в denominator.

Верни:
1. pandas-код функции calculate_retention_d7(events);
2. таблицу users_registered, users_retained_d7, retention_d7;
3. коротко объясни крайние случаи.

Проверь:
дубликаты, несколько регистраций и события около полуночи.
```

## 4. SQL

Для SQL лучше сразу указать:

- диалект;
- схему таблиц;
- ключи;
- ожидаемый grain результата;
- ограничения на CTE/window functions;
- что делать с дублями и NULL;
- нужен ли только запрос или ещё объяснение.

Пример:

```text
Напиши PostgreSQL-запрос.

orders:
order_id, user_id, status, amount, updated_at

Нужно получить одну строку на user_id.
Сначала для каждого order_id оставить запись с максимальным updated_at.
После этого учитывать только status = 'paid'.
Верни total_revenue и paid_orders.

Не фильтруй status до дедупликации.
Верни только SQL и затем 3 коротких пункта с объяснением.
```

## 5. Python и pandas

Полезно сообщить:

- версии библиотек, если совместимость важна;
- имя функции и сигнатуру;
- входной и выходной тип;
- можно ли изменять исходный DataFrame;
- нужно ли избегать циклов;
- должен ли код быть исполняемым целиком.

Пример:

```text
Используй pandas.

Определи:
calculate_metrics(df: pd.DataFrame) -> pd.DataFrame

Не изменяй исходный df.
Код должен быть самодостаточным и исполняемым.
После кода перечисли 3 возможных edge case.
```

Для отладки вставляй:

```text
1. минимальный код;
2. полный traceback;
3. ожидаемое поведение;
4. фактическое поведение;
5. версии Python/библиотеки, если это релевантно.
```

## 6. Статистика

Не пиши просто:

```text
проверь статистически
```

Если метод должен быть определён заранее, укажи его:

```text
Используй двусторонний z-test долей, alpha=0.05.
Верни estimate B-A, test statistic, p-value и 95% CI.
Не объявляй победителя только по point estimate.
```

Если выбор метода входит в задачу:

```text
Сначала выбери подходящий тест и объясни выбор.
Проверь допущения.
Если данных недостаточно для строгого вывода, скажи это явно.
```

## 7. Визуализация

Укажи:

- что должно быть на осях;
- единицы;
- количество графиков;
- нужна ли одна Figure;
- ограничения библиотеки;
- какие числа график обязан отображать.

Пример:

```text
Создай один matplotlib Figure с двумя axes в один ряд:
1. conversion A/B;
2. ARPU A/B.

Высота bar должна равняться рассчитанным значениям.
Верни fig, но не вызывай plt.show().
```

## 8. Работа с файлами

Добавление:

```text
/attach C:\Data\sample.csv
```

Список:

```text
/attach
```

Очистка:

```text
/attach clear
```

После attach в prompt лучше явно сослаться на файл:

```text
Проанализируй прикреплённый sample.csv.
Сначала опиши структуру данных, затем выполни EDA по указанным правилам.
```

Не заставляй модель угадывать, какой из нескольких файлов главный.

## 9. Tools

Режимы:

```text
/tools off
/tools safe
/tools exec
/tools write
/tools full
```

`safe`:

- calculator;
- read_file;
- list_directory;
- search_files.

Начиная с v17.2, чтение пути **вне Workspace** требует явного подтверждения `READ`.

`exec` добавляет Python. Каждый запуск требует `RUN`.

`write` разрешает запись только в Workspace и требует `WRITE`.

`full` объединяет exec + write.

Важно: `python -I` и очищенное окружение являются defense-in-depth, но не полноценной OS sandbox. Не подтверждай выполнение незнакомого опасного кода.

## 10. Structured output

Для JSON:

```text
/format json
```

Для schema:

```text
/format schema C:\Schemas\result.json
```

Отключение:

```text
/format off
```

Даже при structured output полезно прямо написать в prompt, какие поля означают что.

## 11. FAST

Подходит для:

- переписывания текста;
- извлечения фактов;
- простых вычислений;
- небольших pandas/SQL фрагментов;
- резюме;
- обычных вопросов;
- быстрых проверок.

Пример:

```text
Перепиши этот абзац проще, сохрани смысл и длину до 120 слов.
```

## 12. THINK

Подходит для:

- A/B анализа;
- статистики;
- сложного SQL;
- архитектуры кода;
- поиска причин ошибки;
- многошагового продуктового анализа;
- задач с несколькими связанными ограничениями.

THINK всё ещё ограничен одним context/output window.

Если progress показывает `length`, а final не начался, задача может требовать ULTIMATE.

## 13. ULTIMATE

Используй, когда:

- задача объективно большая;
- THINK уже показал truncation;
- нужен полный результат, а не one-shot benchmark;
- время менее важно, чем завершение.

ULTIMATE переносит компактный reasoning checkpoint в новый контекст и продолжает работу.

Не используй ULTIMATE для каждого вопроса: дополнительное reasoning не гарантирует лучшего результата и может увеличивать latency.

## 14. Как управлять контекстом

Prompt + история + attachments + ответ конкурируют за одно context window.

Текущий prompt показывает примерную загрузку:

```text
Вы [THINK | qwen... | CTX 37%] ›
```

При высокой загрузке:

- открой новый диалог, если старый контекст уже не нужен;
- убери ненужные attachments;
- не вставляй большие логи целиком, если достаточно релевантного фрагмента;
- для тяжёлой задачи используй ULTIMATE вместо бессмысленного повышения `num_predict`, если потолок именно `context_window`.

## 15. Плохие и хорошие формулировки

Плохо:

```text
посмотри данные и скажи что думаешь
```

Лучше:

```text
Проанализируй воронку.
Рассчитай conversion между соседними этапами.
Найди максимальную относительную потерю.
Предложи ровно 3 гипотезы и по 1 проверке на каждую.
Верни расчёты с точностью до 1 знака после запятой.
```

Плохо:

```text
напиши код чтобы работало
```

Лучше:

```text
Исправь функцию ниже.
Не меняй публичную сигнатуру.
Сначала найди причину traceback, затем верни полный исправленный код.
Добавь 3 минимальных regression test.
```

## 16. Когда просить модель перепроверить ответ

Полезно для:

- статистики;
- денежных расчётов;
- дат;
- join/deduplication;
- SQL с оконными функциями;
- edge cases.

Пример:

```text
Перед финальным ответом независимо перепроверь denominator, знаки разностей и округление.
```

Это инструкция к качеству конечного результата, а не просьба показывать внутреннее reasoning.

## 17. Конфиденциальность

BULL работает с локальными моделями, но tools могут читать локальные файлы.

Перед `READ`, `RUN` или `WRITE` смотри, что именно клиент предлагает разрешить.

Не помещай токены, пароли и private keys в prompt. Перед отправкой исходников
облачной LLM удаляй секреты, адреса соединений и личные данные.

## 18. Быстрые рабочие рецепты

### Аналитика

```text
/think on
/tools exec
/attach C:\Data\case.csv
```

Затем подробный аналитический prompt.

### Код

```text
/think on
/tools exec
```

Вставь код + traceback + ожидаемое поведение.

### Очень тяжёлый кейс

```text
/ultimate on
```

### Сравнение моделей

```text
/bench single
```

Сначала установи и выбери точную версию набора. `analytics_case` находится в
`bull_extended_core@1.0.0`, использует `analytics_case_v3` и требует явного согласия
на исполняемые проверки движка. Это не OS-песочница; для недоверенного кода нужна VM.
Тест задаёт минимум 16384 токена контекста и обязательный финальный ответ.
Pipeline `ultimate` исследует также возможности восстановления BULL, а не только
один native-ответ модели. Native и final/recovery оцениваются раздельно.
Для обычного сравнения используй **Главная → Тестирование моделей → Сравнить по набору**;
план показывает конкретные задания, параметры и разрешения до запуска.

## 20. Встроенный prompt прямо показывает режим

В рабочем чате строка ввода показывает:

```text
Вы [THINK | qwen... | CTX 37%] ›
```

Это сделано специально, чтобы не помнить состояние клиента.

Перед тяжёлой задачей проверь:

- правильную модель;
- FAST / THINK / ULTIMATE;
- загрузку context;
- attachments;
- tools mode.

Если не уверен:

```text
/help modes
/help prompts
/status
```
