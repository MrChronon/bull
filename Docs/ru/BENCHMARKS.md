# Бенчмарки и пользовательские тесты

## Какие показатели разделяет BULL

- **Native model quality** оценивает первый ответ модели.
- **Final system quality** оценивает результат после разрешённой помощи клиента.
- **Recovery metrics** описывают retries, finalizer, restart и transport recovery.
- **Performance metrics** описывают load, скорость генерации, latency, GPU и VRAM.

Эти пространства нельзя объединять в один score. Техническое завершение генерации,
структура задания и корректность terminal JSON/schema также фиксируются отдельно.

## Стандартное сравнение

Для выбора модели используйте минимум три сопоставимых seed. BULL показывает
среднее, sample SD, min/max, worst seed, rank stability при достаточных данных и
Pareto с учётом неопределённости. Warm определяется по фактическому load duration,
а не по позиции seed. Job-level counterbalancing уменьшает влияние порядка
тестов и моделей на новые прогоны.

В терминале и HTML есть прозрачные относительные профили:

- Качество;
- Скорость с обязательным quality/task gate;
- Баланс;
- Мало памяти;
- собственные веса качества, скорости, надёжности и памяти.

Вывод относится только к моделям и условиям конкретного отчёта.
Неизвестная VRAM не трактуется как малое потребление: профиль **Мало памяти**
недоступен, пока в отчёте нет сопоставимых измерений памяти.

## Пользовательская задача `.txt`

Поместите один UTF-8 prompt в `UserTests/name.txt`. BULL без изменений отправит
его выбранным моделям, измерит runtime и сохранит ответы. Автоматический quality
score не создаётся, потому что детерминированный контракт не задан.

Формат подходит для исследования, творческого текста, консультации и новой
задачи, критерии которой ещё не формализованы.

В `UserTests` есть три самодостаточных синтетических примера: извлечение полей,
структурированный расчёт и деловой перевод. В имени есть `.example.`, поэтому
BULL не запускает их, пока вы не скопируете и не переименуете нужный файл.

## Пользовательский тест `.yaml`

Структурированный тест использует безопасный формат `bull-user-test` version 1.
Новые файлы оцениваются строгим `user_contract_v2`; сохранённые результаты
`user_contract_v1` сохраняют записанную интерпретацию и не пересчитываются молча.
Парсер не поддерживает custom tags, anchors, aliases, исполняемый код и регулярные
выражения. Размер файла ограничен 256 KiB, prompt — 50 000 символов, критериев
может быть от одного до двадцати, сумма весов должна быть ровно 100.

Поддерживаемые критерии:

| Тип | Условие успеха | Обязательные поля |
| --- | --- | --- |
| `contains_all` | все фразы встречаются без учёта регистра | `values` |
| `contains_any` | встречается хотя бы одна фраза | `values` |
| `forbidden_any` | не встречается ни одна запрещённая фраза | `values` |
| `word_count` | число слов входит в закрытый диапазон | `min`, `max` |
| `terminal_json_equals` | значение по JSON path равно ожидаемому | `path`, `expected` |
| `terminal_json_number` | число по JSON path входит в допуск | `path`, `expected`, один допуск |

Для `terminal_json_number` задаётся ровно одно поле: `tolerance_abs` или
`tolerance_pct`. Поддерживаются вложенные пути вида `result.max_stress_mpa`.

`critical: true` ограничивает автоматический score значением 59%, если критерий
провален. Используйте его только для ошибки, делающей ответ непригодным для задачи.

`manual_review` перечисляет важные вопросы, которые невозможно честно проверить
детерминированно. Они не получают скрытого веса и явно требуют проверки человеком.

Для `terminal_json_*` после `BENCHMARK_RESULT` должен быть финальный JSON без
дополнительного текста. Сравнение строго учитывает тип: JSON `true` не равно
числу `1`. Проверка одного JSON path подтверждает только это значение, а не всю
схему объекта.

Пример:

```yaml
schema: bull-user-test
version: 1
id: my_calculation
title: My calculation
description: One reproducible synthetic task
language: ru
prompt: |
  Рассчитай значение по исходным данным.
  Объясни метод и верни result.value в terminal JSON.
criteria:
  - id: numeric_result
    type: terminal_json_number
    description: Итог входит в заранее заданный допуск
    weight: 100
    path: result.value
    expected: 42
    tolerance_abs: 0.1
    critical: true
manual_review:
  - Проверить метод и допущения.
```

Если нужен terminal JSON, BULL добавляет к эффективному prompt только технический
контракт вывода. Исходный файл, hashes и точный эффективный prompt сохраняются в checkpoint.

## Правила написания

1. Проверяйте одну рабочую задачу, а не профессию целиком.
2. Дайте все входные данные, единицы, обозначения и допустимые предположения.
3. Отделите содержание от формата ответа.
4. Укажите, что нельзя предполагать или придумывать.
5. Зафиксируйте эталон и допуск до просмотра ответов моделей.
6. Используйте синтетические или разрешённые данные без секретов и персональной информации.
7. Каждый критерий должен отвечать на один однозначный вопрос.
8. Вес отражает влияние на реальную задачу, а не удобство автоматизации.
9. Совпадение ключевых слов не доказывает правильность рассуждения.
10. Однословные literal-критерии ищутся по Unicode-границам слова: `ты` не
    совпадает с «Документы». Это буквальная проверка, а не оценка языка или смысла.
10. Неформализуемые свойства переносите в `manual_review`.

Сначала выполните быстрый прогон и проверьте false positive/negative, затем
используйте три seed. Изменение prompt или scorer создаёт новую версию теста;
старые результаты нельзя молча переинтерпретировать.

## Результаты и публикация

Сводка в терминале и HTML строятся из одних сохранённых records. Summary JSON и
HTML предназначены для контролируемого обмена. Raw JSON, checkpoints, private
evidence, ответы, prompts, endpoints и пути могут содержать приватные данные.

Встроенные packs версионируются и проверяются по hashes. Data-only pack не может
исполнять Python. Перевод candidate в stable требует валидации, golden snapshots,
regression scorer, проверки false positive/negative и версионированного решения.
