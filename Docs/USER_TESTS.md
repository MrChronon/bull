# Пользовательские тесты BULL

Этот формат нужен для практического вопроса: **какая из установленных моделей
лучше решает именно мои задачи?** Файлы помещаются в `UserTests` и появляются в
меню **Тестирование моделей → Задача из UserTests**.

## Два уровня

### `.txt`: простой prompt

Один UTF-8 файл — один prompt. BULL отправляет неизменный текст выбранным моделям,
сохраняет ответы и измеряет runtime. Автоматического quality score нет: без
эталона или проверяемого контракта такой балл был бы выдуманным. Ответы можно
просмотреть рядом и оценить вручную.

Подходит для первого исследования задачи, творческого текста, консультации и
любого случая, где критерий «хорошо» пока не формализован.

В `UserTests` есть три самодостаточных синтетических примера: извлечение полей,
структурированный расчёт и деловой перевод. Их имена содержат `.example.`,
поэтому BULL их не запускает: скопируйте нужный файл и переименуйте копию.

### `.yaml`: структурированный тест

YAML содержит prompt и детерминированные критерии. Новые файлы оцениваются
контрактом `user_contract_v2`; результаты, уже записанные как
`user_contract_v1`, сохраняют прежнюю интерпретацию и не пересчитываются молча.
BULL использует безопасное
подмножество YAML собственной реализации: без тегов, anchors, aliases,
исполняемого кода и регулярных выражений. Файл ограничен 256 KiB, prompt — 50 000
символов, критериев может быть от 1 до 20. Их веса должны в сумме давать ровно
100.

Поддерживаются только проверки:

| `type` | Что считается успехом | Обязательные поля |
|---|---|---|
| `contains_all` | В тексте есть все фразы без учёта регистра | `values` |
| `contains_any` | Есть хотя бы одна фраза | `values` |
| `forbidden_any` | Не встречается ни одна запрещённая фраза | `values` |
| `word_count` | Число слов входит в закрытый диапазон | `min`, `max` |
| `terminal_json_equals` | Значение по JSON path точно совпало | `path`, `expected` |
| `terminal_json_number` | Число по JSON path попало в допуск | `path`, `expected` и ровно один из `tolerance_abs`/`tolerance_pct` |

`critical: true` означает, что провал проверки ограничивает автоматический балл
значением 59%. В отчёте сохраняются criterion, причина и наблюдаемое значение.
Это правило задаёт автор теста, поэтому применять его следует только к ошибке,
которая действительно делает ответ непригодным.

`manual_review` — список важных вопросов, которые нельзя честно проверить
описанными правилами. Он не получает скрытого численного веса и всегда помечает
результат как требующий просмотра человеком.

Для `terminal_json_*` строка `BENCHMARK_RESULT` должна содержать последний
смысловой блок ответа: после завершающего JSON-значения нельзя дописывать текст.
`terminal_json_equals` проверяет типы строго: JSON `true` не равно числу `1`.
Одна JSON-проверка пути не подтверждает всю схему объекта — объявляйте отдельные
критерии только для значений, которые действительно важны.

## Как писать хороший prompt

1. Опишите одну проверяемую рабочую задачу, а не профессию целиком.
2. Дайте все исходные данные, единицы, обозначения и допустимые допущения.
3. Отделите требования к содержанию от формата ответа.
4. Укажите, чего модель не должна предполагать или придумывать.
5. Для расчётов задайте ожидаемые JSON-поля и единицы.
6. Используйте синтетические или разрешённые к распространению данные.
7. Не включайте пароли, ключи, персональные данные и конфиденциальные документы.
8. Проверьте эталон и допуски независимо минимум один раз.
9. Не используйте `contains_*` как замену смысловой проверке: совпадение слов не
   доказывает корректность рассуждения.
10. Сначала выполните быстрый прогон, затем стандартные три seed.

## Как выбирать критерии

- Каждый критерий должен отвечать на один вопрос и иметь однозначный результат.
- Вес отражает важность ошибки для реальной задачи, а не удобство проверки.
- Числовой допуск должен происходить из предметной области или точности входных
  данных. Не подбирайте его после просмотра ответов моделей.
- `terminal_json_equals` подходит для enum, boolean и точных идентификаторов;
  тип значения имеет значение, поэтому `true` и `1` различаются.
- `terminal_json_number` подходит для вычислений; путь может быть вложенным,
  например `result.max_stress_mpa`.
- Одно слово в `values` ищется как отдельное слово, а не как часть другого:
  `ты` не совпадает с «Документы». Это буквальная проверка, не оценка языка или
  смысла. Формулировки для `forbidden_any` всё равно должны быть достаточно
  специфичными, иначе корректное опровержение может дать ложное срабатывание.
- Если важное свойство нельзя проверить детерминированно, перенесите его в
  `manual_review`, а не создавайте фиктивный автоматический критерий.

## Минимальный YAML

```yaml
schema: bull-user-test
version: 1
id: my_calculation
title: My calculation
description: One reproducible synthetic task
language: ru
prompt: |
  Рассчитай значение по приведённым данным.
  Объясни ход решения и верни result.value в terminal JSON.
criteria:
  - id: numeric_result
    type: terminal_json_number
    description: Итог попадает в заранее установленный допуск
    weight: 100
    path: result.value
    expected: 42
    tolerance_abs: 0.1
    critical: true
manual_review:
  - Проверить корректность метода и применимость допущений.
```

Если используется `terminal_json_*`, BULL добавляет к prompt только техническое
требование завершить ответ строкой `BENCHMARK_RESULT` и одним JSON-объектом с
перечисленными путями; после объекта не должно быть дополнительного текста.
Исходный файл, вычисленные хэши и точный текст эффективного prompt фиксируются
в checkpoint.

## Интерпретация

Автоматический score YAML относится только к объявленным машинным проверкам. Он
не является универсальной оценкой знаний модели. Для `.txt` BULL показывает
runtime и ответы, но не создаёт quality-рейтинг. Профили «Качество», «Скорость»,
«Баланс» и «Мало памяти» доступны только когда прогон содержит сопоставимый
Native quality score.
